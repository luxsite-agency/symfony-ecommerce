# Пак магазину і реєстр магазинів

Система магазинів Symfony ecommerce LuxSite (ADR v2, розділ «Система магазинів» у `docs-adr.md`): один рушій з версіями,
кожен магазин — окремий стек і окремий **пак** (приватний репо `example-org/store-<key>`), усі магазини — у **реєстрі**
`stores.yaml` цього репо. Команди — `bin/store`; деплой, бекап, архів — `docs/store-ops.md`.

## Реєстр `stores.yaml`

Одне місце правди для `bin/store` і агентів: де живе магазин, на якій версії рушія, у якому статусі. Секретів у реєстрі нема.
Зміни — PR-ом у рушій. Перевірка: `bin/store validate`.

```yaml
version: 1
stores:
    - key: shop1                       # a-z, 0-9, '-', до 31 символу
      name: 'Назва магазину'
      repo: example-org/store-shop1 # пак на GitHub (приватний)
      pack: <робоча копія>  # необов'язково: локальна копія паку, має пріоритет над repo
      server:
          host: prod-host               # ssh-аліас; local — ця машина (стенд на dev-сервері: path /srv/stores/<key>)
          user: deploy                 # не root; користувач у групі docker
          path: /work/stores/shop1     # нова схема — завжди /…/stores/<key>
          proxy: traefik               # traefik (наш сервер) | standalone (Caddy з TLS, сервер клієнта)
          traefik_network: edge        # необов'язково (типово edge); старий прод-сервер — edge
          certresolver: ''             # необов'язково (порожньо — TLS без резолвера); старий прод-сервер — letsencrypt
      domains: { site: shop1.example.com, admin: admin.shop1.example.com }
      locales: [uk, en]                # перша — за замовчуванням
      engine: v1.0.0                   # тег рушія (або sha коміту до тегів)
      status: active                   # active | archived | handed-over
      support: true                    # на нашій підтримці
      backup_target: /srv/stores/_copies/shop1   # /шлях на машині, звідки запускають bin/store (dev-сервер), host:/шлях або null
      notes: 'вільний текст'
```

Правила (перевіряє `bin/store validate`):
- обов'язкові всі поля, крім `pack` і `notes`; невідомі поля — помилка (друкарська помилка не має тихо вимкнути поле);
- `active` — лише шлях `/…/stores/<key>` і не `root`; стара схема (legacyshop: `/work/shop-engine`) допустима лише для `archived`,
  і `deploy/backup/restore/archive` для неї відмовляють завжди;
- `handed-over` ⇒ `support: false`; `site` ≠ `admin`; домени не повторюються між неархівними магазинами;
- значення й імена ключів, схожі на секрети (паролі, токени, `://user:pass@`, приватні ключі), — помилка.

## Структура паку

```
store-<key>/
├── store.yaml                 # format, key, name, locales, domains, engine (+ addons) — без сервера/статусу (це реєстр)
├── config/parameters.yaml     # → config/store/parameters.local.yaml образу
├── themes/<key>/              # → public/themes/<key>/ образу: лого, шрифти woff2, банер, theme.css
├── themes/<key>/templates/    # необов'язково: своя верстка (Twig поверх рушія, @engine) → templates/store/ образу; docs/themes.md
├── themes/<key>/theme.yaml    # маніфест теми (пише bin/store theme new)
├── catalog/*.csv              # початковий каталог (catalog:import:feed), external_id/sku обов'язкові
├── catalog/demo-images/       # лише демо-магазин: справжні фото для app:demo:seed (<KEY>-<n>.jpg, category-<key>.jpg,
│                              # post-<key>.jpg + CREDITS.md з джерелами й ліцензіями) → config/store/demo-images/ образу
├── content/                   # сторінки (pages/*.md), тексти категорій (categories/<slug>.md), блог
├── seo/                       # семантика, meta.csv, технічні зауваження
├── studio/                    # персона (verified_facts) і промпти зовнішньої контент-панелі (YAML), без токенів
├── docs/brief.md              # бриф: кожен факт для сайту — з джерелом
├── docs/CLAUDE.md             # правила агента магазину
└── docs/launch-checklist.md   # чекліст запуску (у шаблоні)
```

`src/Store/` (клієнтський PHP) у паку v1 **не використовується**: у рушії для нього нема міграцій
(розбір консиліуму 06.10, п. 8). Потрібна функція — PR у рушій. Свій дизайн — є: Twig-шаблони в `themes/<key>/templates/`
(розділ «Свій дизайн»), без PHP.

### Свій дизайн (шаблони паку), 11.10.2026

Рішення власника 11.10.2026: будь-який магазин може ввімкнути власний дизайн, відмінний від типового. Три рівні, від дешевого:

1. **Кольори, лого, картинки** — `app.theme` у `config/parameters.yaml` + файли в `themes/<key>/` (як було).
2. **CSS поверх типової верстки** — `app.theme.stylesheet: themes/<key>/theme.css` + клас `body.theme-<key>` (як було).
3. **Своя верстка** — `themes/<key>/templates/` у паку: файл з тим самим шляхом, що в рушії (`site/home.html.twig`,
   `site/base.html.twig`, `site/catalog/product_show.html.twig`, `site/partials/_product_card.html.twig`…), перекриває шаблон рушія.
   Частково: `{% extends '@engine/site/home.html.twig' %}` і свої блоки; повністю: свій файл без `extends` (змінні контролера
   ті самі — коментар-контракт на початку шаблону рушія). Власні partial-и паку — у `site/partials/`.

**Команда:** `bin/store theme new <key>` створює тему в паку — `themes/<key>/theme.css` (якщо нема), заготовки
`site/base.html.twig`, `site/home.html.twig` як `{% extends '@engine/…' %}` з усіма блоками = `parent()` (інші шаблони —
аргументами, перелік і блоки — `bin/store theme list`) і маніфест `themes/<key>/theme.yaml`; `--copy <шаблон>` — повна копія для
сторінки, де дизайн справді інший. Після оновлення рушія `bin/store theme diff <key>` показує, які перекриті файли й блоки
змінились у рушії з версії `engine:` маніфесту (extends-заготовки підхоплюють неперекриті блоки самі, повну копію зливати
руками). Модель спільна з service-engine (`bin/site theme`, 11.10.2026); заборонена зона для теми — кабінет (`site/account/`),
schema.org (`_schema*`), sitemap, листи й адмінка (вони в рушії, не в шаблонах паку).

Правила: лише `site/**`, лише `*.twig`; файл без відповідника в рушії — попередження валідатора (новий partial — норма, одрук —
ні); `extends` самого себе без `@engine` — помилка. Зміна `themes/<key>/templates/` змінює хеш паку → `bin/store deploy`
перезбирає образ: `lint:twig` у збірці, у кандидаті `store:validate` і `store:smoke`; помилка — реліз не вмикається. Ризик
рівня 3: повна копія не отримує виправлень рушія автоматично — після оновлення рушія звіряти `bin/store theme diff` (CI рушія
лінтить лише фікстуру `tests/store/pack-demo/themes/demo/templates`; паки перевіряє їхній деплой). Після зміни дизайну на
проді — `/analytics-healthcheck`. Контракт блоків, змінних і класів, чутливі зони — `docs/themes.md`.

### `store.yaml`
```yaml
format: 1
key: shop1
name: 'Назва'
locales: [uk, en]
domains: { site: shop1.example.com, admin: admin.shop1.example.com }
engine: v1.0.0      # версія рушія, з якою пак перевірено
addons: [gmb-reviews]   # необов'язково: аддони рушія (docs/addons.md), ставляться у збірці образу
```
`locales` мають збігатися з реєстром (помилка). `domains` у паку — бойові; реєстр може задати інші (стенд, технічний домен, відновлення на dev-сервері) — тоді попередження, деплой бере хости з реєстру. `engine` може тимчасово розходитися під час оновлення (попередження).

### `config/parameters.yaml`
- лише `parameters:`; лише параметри, які знає рушій (`config/services.yaml`); `app.locales` = `locales`, `app.default_locale` = перша мова;
- мова адмінки — окремо від мов контенту: `app.admin_locales` (рушій: uk, en, ru; пак не задає). Типова — `app.default_locale`, якщо адмінка
  нею перекладена, інакше en (en-pharmacy: en). Менеджер перемикає мову в меню користувача, вибір зберігається в профілі;
  нова мова адмінки — лише з повними `translations/admin+intl-icu.*` і `validators.*` (стереже `AdminTranslationCoverageTest`);
- **без `admin_host`/`site_host`**: їх дописує деплой із `domains` реєстру (той самий пак піднімається на стенді й технічному домені);
- **без секретів**: ключі НП, KeyCRM, пошти — `.env.local` на сервері магазину (600) або Settings адмінки;
- `app.theme` — лише ключі `SiteTheme::DEFAULTS`. Невідомий ключ — помилка і в `bin/store validate`, і в рушії (SiteTheme кидає виняток),
  щоб перейменування ключа в новій версії рушія не ламало вигляд магазину непомітно. `app.theme.key` = ключ магазину;
  файли теми — рядки `themes/<key>/…`, мають існувати в паку;
- **`app.theme.logo.src` обов'язковий** (правило власника 09.10.2026: у шапці кожного сайту — знак, не назва текстом) і лежить у
  `themes/<key>/`; без нього падають і `bin/store validate`, і сам рушій (`SiteTheme`). Нейтральний `assets/logo.svg` рушія — лише для dev.
- `app.license` — реквізити сайту для сторінки `/license` (з підвалу на неї посилається лише режим «Повний» налаштування «Рядок платформи у футері», типове — «Коротко») і сторінки «Ліцензія» в
  адмінці (меню «Налаштування», рядок у підвалі адмінки). Код рушія — Apache 2.0 для всіх сайтів, тут лише власник сайту й договір
  з LuxSite на обслуговування. Необов'язковий; без нього `bin/store validate` попереджає, власником на сторінці стає `app.site_name`,
  договір — «не вказано». Ключі:
  ```yaml
  app.license:
      licensee: { uk: 'ФОП Прізвище І. Б.', en: 'Sole proprietor …' }   # або один рядок для всіх мов
      type: subscription            # договір з LuxSite: subscription | perpetual; порожньо → «не вказано»
      contract: '№ 12 від 01.02.2026'
      since: '2026-02-01'           # 'YYYY-MM-DD' у лапках
  ```
  Невідомий ключ, інший `type` чи дата не за форматом — помилка валідатора, а в рушії виняток на сторінці ліцензії
  (`App\Core\License\PlatformLicense`). Текст ліцензії (uk, en; інші мови сайту → en) — у рушії, `templates/license/`, пак його не
  перекриває; сторонні компоненти — `bin/console license:components` у збірці образу. Наших контактів на сторінці нема — лише
  посилання на luxsite.agency.
- `app.page_path_prefix` — адреса статичних сторінок (Page): типово `''` → у корені `/{slug}/` з кінцевим слешем, `/ru/{slug}/`
  (рішення власника 20.10.2026: «page не повинно бути в структурі URL»; паки demo, partner-shop, legacyshop і шаблон
  `store-template` задають `''` явно). `'/<слаг>'` → `/<слаг>/{slug}` без кінцевого слеша — лише для сайту, що переїжджає зі своєю
  старою структурою. Стара адреса `/page/{slug}` (посилання в Google) — 301 на чинну адресу завжди, хай який префікс (крім самого
  `'/page'`); якщо слаг відтоді змінено — одним кроком на нову адресу за редиректом зміни слага. У корені
  `/{slug}/` спершу шукає опубліковану сторінку, потім категорію; слаг сторінки не може збігатися з кореневою категорією, товаром
  чи службовою адресою (валідатор адмінки, той самий список `ReservedPathSegments`, що для каталогу), і навпаки — товар чи
  коренева категорія не забирають слаг сторінки. Адреса сторінки без кінцевого слеша (`/{slug}`) розбирається як товар і дає 404 без 301 — так само, як для категорій (рішення власника); старі посилання без слеша при міграції сайту закривати ручними редиректами. Інше значення, ніж `''` чи `/<слаг>`, — помилка
  рушія. Перемикати на живому сайті — лише з перевіркою колізій слагів (сторінки, що вже збігаються з категоріями, лишаться
  перед категоріями).

Схема ключів теми для валідатора — `config/store/theme-schema.json` (генерує `bin/console store:validate --schema`,
синхронність із `SiteTheme::DEFAULTS` тримає `SiteThemeTest`). Новий ключ теми в рушії = правка DEFAULTS + перегенерувати схему.

### Ліміти й заборони
Пак ≤ 50 МБ, файл ≤ 5 МБ (фото товарів — імпортом за URL/з теки, не в паку). Заборонені `.env*`, `.secrets`, `*.pem`, `*.key`,
SSH-ключі, `*.sql(.gz)`, символьні посилання; текстові файли скануються на секрети.

### Джерело правди
Git паку тримає тему, параметри й **початкові** дані. Після першого імпорту каталог, тексти, переклади й мета живуть у БД магазину
(адмінка, CRM); деплой БД не чіпає. Правки на проді переносяться в пак лише як історія чи для нових магазинів.

## Команди

| Команда | Що робить |
|---|---|
| `bin/store validate` | реєстр |
| `bin/store validate <key>` | реєстр + пак магазину (поле `pack`) |
| `bin/store validate <тека>` | пак у теці (шаблон, новий пак до запису в реєстр) |
| `bin/store validate --all` | реєстр + усі паки з локальною копією (CI рушія) |
| `bin/store new <key> <домен> [--name=… --admin=… --locales=uk,en --from=template\|<тека> --dir=… --github]` | пак із шаблону |
| `bin/console store:validate [--schema]` | тема зібраного розгортання: ключі й файли під `public/` (health-check образу) |

`bin/store validate` потребує лише `python3` і PyYAML (як і решта `bin/store`), без PHP і Docker.

### `bin/store new`
1. Копіює `store-template/` (або `--from=<тека паку>`) у `$STORE_PACKS_DIR/store-<key>` (типово поточна тека) без `.git` і `.env*`.
2. Перейменовує `themes/<зразок>` → `themes/<key>`, підставляє ключ, домени, назву, мови, версію рушія (поточний тег або sha).
3. Перевіряє пак; якщо помилки — тека не створюється. `git init`, перший коміт.
4. `--github`: `gh repo create example-org/store-<key> --private` + доступ команді `developers` + push. Без прапорця — лише локально.
5. Друкує запис для `stores.yaml` (додати PR-ом; `server` і `backup_target` уточнити).

`DRY_RUN=1` — лише показати дії. Зразок `--from=<пак>`: ключ підставляється як ціле слово — короткий загальний ключ (`shop`)
зачепить зайве, перевірте `git diff` нового паку.

## Шаблон `store-template/`

Живе в репо рушія, бо версіонується разом з ним: CI рушія перевіряє, що шаблон проходить `validate` на поточних ключах теми.
Токени шаблону — `storetemplate`, `storetemplate.example.com`, `admin.storetemplate.example.com`, `Store Template`.
Тексти-заготовки мають плейсхолдери `[…]` — публікувати лише після заміни перевіреними фактами (чекліст запуску, п. 11).
Онлайн-оплати в шаблоні нема: v1 продає з COD, безготівкою і Новою поштою (LiqPay — окремий епік після етапу 1).
