# AI на ключі магазину (BYOK, E15)

Вбудовані AI-функції адмінки працюють на ключі **OpenRouter** клієнта і за рахунок його кредитів. Агенція ключа не дає
і витрат не несе; без ключа AI-кнопок в адмінці нема. Провайдер у v1 один — OpenRouter (через нього доступні моделі
Anthropic, OpenAI, Google, DeepSeek тощо); клієнт OpenAI-сумісний, інший провайдер пізніше — лише base URL.

## Налаштування (адміністратор → Налаштування сайту → група «AI»)

| Ключ | Що |
|---|---|
| Ключ OpenRouter | `sk-or-v1-…` з [openrouter.ai/keys](https://openrouter.ai/keys). Зберігається шифровано, показується лише маскою `…a1b2`. Порожнє поле при збереженні — лишити чинний; перемикач «Видалити збережений ключ» — прибрати. |
| Модель AI | `vendor/model` з [openrouter.ai/models](https://openrouter.ai/models). Порожньо — `app.ai_default_model` (типово `deepseek/deepseek-v4-pro`). |
| Місячний ліміт витрат, $ | Коли сума `cost` успішних викликів за календарний місяць досягає ліміту, виклики відхиляються до першого числа. 0 або порожньо — без ліміту. Ліміт на самому ключі OpenRouter (Credit limit) — додаткова страховка, його рушій не перевіряє. |

Кнопка **«Перевірити з'єднання»** під списком — `GET /api/v1/key` OpenRouter: підпис ключа, ліміт і витрати на ключі.
Токенів не витрачає, у журнал пише рядок `check`. Текст від провайдера у flash екранується. Поруч — витрати за місяць;
якщо провайдер для якихось викликів не повернув `usage.cost`, їх кількість показується окремо: у ліміті вони не враховані.

## Як зберігається ключ

- У БД — конверт `enc:v1:<4 останні>:<base64>`: `sodium_crypto_secretbox` (XSalsa20-Poly1305), ключ шифрування —
  env `SETTINGS_SECRET_KEY` (32 байти base64) **лише в `.env.local` 600** на сервері магазину. Не `APP_SECRET` і не похідна
  від нього. Перший деплой генерує сам; для магазинів, розгорнутих раніше, `bin/store deploy` дописує; вручну —
  `bin/console app:secrets:keygen`. `bin/store doctor` попереджає, якщо ключа нема.
- `Settings::get()` для секретного ключа повертає **маску**, тож шаблони, Admin API чи MCP значення не віддадуть; відкритий
  текст — лише `Settings::secret()`, який викликає тільки клієнт OpenRouter.
- Дамп БД (`bin/store backup`) містить лише конверт; `.env.local` у бекап не входить.
- Зміна ключа — у `security_audit` (`settings.secret_set` / `settings.secret_cleared`: `user_id`, HMAC email, маска; без значення).
- Логи: HttpClient заголовків не пише; `SecretRedactProcessor` додатково замінює відкриті секрети маскою у повідомленнях
  і контексті Monolog.
- Без `SETTINGS_SECRET_KEY` секретне поле в адмінці неактивне, AI вимкнено. Некоректний ключ (не 32 байти base64, перенос
  рядка) — те саме, але адмінка і `bin/store doctor` кажуть саме «некоректний», не «не задано».

## Зміна або втрата `SETTINGS_SECRET_KEY`

Конверт у БД відкривається лише тим ключем, яким його зашифрували. Якщо ключ змінився (перегенерували `.env.local`,
відновили дамп БД на новому сервері — `.env.local` у бекап не входить), застосунок **не падає**: ключ OpenRouter вважається
відсутнім, у «Налаштуваннях сайту» — банер **«Ключ OpenRouter треба ввести знову»** і бейдж «не розшифрувати — введіть
знову», «Перевірити з'єднання» і AI-функції відхиляються з тим самим поясненням (рядок `rejected` у журналі), у
`security_audit` — `settings.secret_unreadable` (код, маска; один запис на процес). Що робити:

- **Ключ втрачено** (старого нема): ввести ключ OpenRouter в адмінці знову — і все.
- **Ключ міняють навмисно (ротація)** — перешифрувати секрети, щоб не вводити їх заново. Ключі передаються лише змінними
  середовища (не аргументами — історія shell, `ps`):
  ```bash
  # 1. новий ключ ще не в .env.local
  NEW=$(bin/console app:secrets:keygen | cut -d= -f2)
  SETTINGS_SECRET_KEY_NEW="$NEW" bin/console app:secrets:rotate --dry-run   # що буде зроблено
  SETTINGS_SECRET_KEY_NEW="$NEW" bin/console app:secrets:rotate             # перешифрувати старим → новим
  # 2. записати $NEW у .env.local як SETTINGS_SECRET_KEY (600), cache:clear / перезапуск php
  ```
  Між кроками 1 і 2 секрети для застосунку «не розшифрувати» — робити поспіль. Якщо `.env.local` уже з новим ключем, а
  старий ще відомий (бекап на новому сервері): `SETTINGS_SECRET_KEY_OLD=… bin/console app:secrets:rotate
  --old-key-env=SETTINGS_SECRET_KEY_OLD`. Конверти, яких старий ключ не відкриває, команда лишає (`--clear-unreadable` —
  стирає); їх усе одно вводити знову. Кожна зміна — `settings.secret_rotated` у `security_audit`. У магазинах команда —
  в контейнері: `docker compose exec -e SETTINGS_SECRET_KEY_NEW="$NEW" php bin/console app:secrets:rotate`.

## Журнал використання

`ai_usage` (меню «AI → Використання AI», видно менеджерам): коли, хто, функція (`describe`, `translate`, `seo`, `check`),
стан (`ok`, `error`, `rejected`), модель, сутність, токени, вартість у кредитах OpenRouter (`usage.cost`), тривалість,
клас помилки. Текстів запитів і відповідей у журналі нема. Зберігання `app.ai_usage_months` (24; 0 — не прибирати),
prune щоночі зі Scheduler.

## Технічні параметри (`config/services.yaml`, для магазину — `config/store`)

`app.ai_base_url`, `app.ai_default_model`, `app.ai_timeout` (с), `app.ai_max_input_chars` (0 — без стелі),
`app.ai_max_output_tokens`, `app.ai_usage_months`.

## Що далі (PR-7, після пакетів змін)

Кнопки у формах товару/категорії/сторінки/поста («Згенерувати / покращити опис», «Перекласти», «SEO title/description»):
виклик через Messenger, результат стає пакетом змін з діфом і типографічними попередженнями, застосовує менеджер.
У запит ідуть лише поля каталогу/контенту, персональні дані покупців — ніколи.
