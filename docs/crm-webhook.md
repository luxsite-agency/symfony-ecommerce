# Вебхук CRM (KeyCRM → магазин): токен, ротація, ліміти

`POST https://<site_host>/webhooks/crm/stock?token=<токен>` приймає зміни залишків від KeyCRM (`CrmWebhookController`,
активний конектор робить перевірку токена й розбір). KeyCRM за офіційною документацією шле лише URL + POST і не підтримує
власних заголовків чи підпису payload, тому токен живе в адресі. Що з цього випливає (консиліум безпеки 10.10, п. 8):

- **Порівняння** лише `hash_equals`, токени після ротації зберігаються в БД sha256-хешем (`crm_webhook_token`).
- **Ліміт з IP** лише на невдалі спроби: `crm_webhook_ip`, 60 відмов (403) на хвилину (framework.yaml), далі 429 з `Retry-After` для всіх запитів з цієї адреси до кінця вікна. Запити з правильним токеном ліміт не списують, тож масове оновлення залишків з KeyCRM проходить.
- **Логи**: nginx магазину не пише access-лог для `/webhooks/` (`map $request_uri $loggable` + `access_log … if=` у `docker/nginx/store.conf`,
  `prod.conf`; перевірка після деплою: `./dc logs nginx | grep token=` має бути порожнім); Symfony логує відмови й результат без токена,
  а `WebhookTokenMaskProcessor` маскує `token=` у будь-якому записі (зокрема `request_uri` при 500). Логи Cloudflare і traefik адресу бачать, тому токен треба ротувати.
- **Додатково** приймається `Authorization: Bearer <токен>` (якщо колись зʼявиться у KeyCRM); не вимагається.

## Ротація

```
./dc exec php bin/console crm:webhook:rotate-token
```

Команда створює новий токен, показує готовий URL для KeyCRM (Налаштування → Вебхуки) і нічого більше не зберігає у відкритому
вигляді. Попередній токен (при першій ротації це `CRM_WEBHOOK_TOKEN` з `.env.local`) діє ще **24 години**, далі відкидається.
Прострочені записи прибираються при наступній ротації. Вивід команди не копіювати в чат і тікети. Ротувати: при підозрі на
витік, при зміні підрядника з доступом до KeyCRM, і планово раз на пів року.

До першої ротації чинний токен береться з env `CRM_WEBHOOK_TOKEN`; порожній env без ротації = вебхук вимкнено (403).
